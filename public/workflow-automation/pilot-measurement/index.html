Workflow automation pilot metrics: a scorecard that separates activity from value.

A run is not a business result. A useful pilot defines which cases are eligible, what proves completion, how much review remains, and what each verified result costs before the first test begins.

Short answer: track eligible cases, verified completions, no-touch completions, exception-review time, team hours returned, runtime, and cost per verified completed case. Set the decision thresholds before seeing pilot results.

The measures

Seven numbers tell a more honest story than “runs completed.”

01

Cases received

All cases presented during the measurement period. Keep this denominator visible so excluded work does not disappear from the report.

02

Eligible cases

Cases that match the scope agreed before the pilot. Record every exclusion reason separately; do not recast a failed case as ineligible after the fact.

03

Verified completions

Eligible cases that reached the intended end state and passed the agreed result check. A click sequence finishing is not enough.

04

No-touch completions

Verified completions that required no teammate handling after the case entered the workflow. Report this as a count and as a share of eligible cases.

05

Exception-review minutes

Active teammate time spent understanding, correcting, approving, or recovering cases. This is labor shifted to review, so subtract it from time returned.

06

Runtime

Elapsed time from an eligible case entering the workflow to its verified result or exception. Report median and a high percentile; do not present runtime as labor saved.

07

Cost per verified completion

Total pilot run cost divided by verified completions. Show failed and excluded cases alongside it so the unit cost cannot hide poor coverage.

The scorecard

Keep the formulas explicit.

Record raw counts and minutes first. Calculate rates only after the denominator is agreed, and preserve exception reasons so a changing case mix is visible.

verified no-touch completions ÷ eligible cases= no-touch completion rate
(manual minutes per case × verified no-touch completions − exception-review minutes)÷ 60 = team hours returned
total measured run cost ÷ verified completions= cost per verified completion

Illustrative example

Make the denominator and review burden visible.

Inputs

  • 100 cases received;
  • 85 cases eligible;
  • 8 manual minutes per case;
  • 45 exception-review minutes; and
  • $70 in measured run cost.

Results

  • 74 verified completions;
  • 70 no-touch completions;
  • 82.4% no-touch completion rate;
  • 8.6 team hours returned; and
  • $0.95 per verified completion.

What it does not prove

  • that excluded cases are solved;
  • that the same rate holds at higher volume;
  • that every exception is safe; or
  • that the pilot met its pre-agreed thresholds.

Example status: these numbers are illustrative math, not a Wexpro customer result. The actual decision depends on thresholds agreed for the workflow’s risk, quality, cost, and case mix.

The decision

Agree on the pass criteria before the pilot starts.

  • Quality: define the observable result and the minimum verified completion rate.
  • Coverage: set the minimum share of received cases that must be eligible.
  • Safety: define actions that remain with a person and failure conditions that stop a case.
  • Labor: set a minimum for net team hours returned after exception review.
  • Economics: set the maximum cost per verified completed case.
  • Scale: increase volume only when every required threshold holds for the agreed measurement window.

Questions

Common workflow pilot measurement questions.

What is a good automation completion rate?

There is no universal rate. The acceptable threshold depends on the workflow’s risk, case mix, manual cost, and the consequence of an incorrect result. Set it before the pilot so the target does not move after results arrive.

Should excluded cases count as failures?

Keep exclusions separate from failures, but show them beside the completion rate. A high completion rate over a small eligible share may still be a poor business result.

Is runtime the same as time saved?

No. Runtime is elapsed system time. Team time returned is active manual time avoided minus active exception-review time. Report both because they answer different questions.

When is a pilot ready to scale?

Only after the agreed quality, coverage, safety, labor, and cost thresholds hold for the chosen measurement window and the remaining exceptions have an explicit owner.
